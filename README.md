# Решение тестового задания
Ускорить ночную синхронизацию сущностей из CRM в PostgreSQL.  
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.

## Что было плохо

### Запрос и коммит на каждую сущность
- На каждого покупателя 1-2 `SELECT` по логину среди сделок, затем `UPDATE`/`INSERT` и `commit`.
- На каждую сделку 1-2 `SELECT` по `crm_lead_id`/логину среди покупателей, затем `UPDATE`/`INSERT` и `commit`.
- При слиянии 2 `commit`, `flush` и ещё `commit`.

### Поиск по JSONB без индексов
Все данные, включая идентификаторы и логины, лежат в JSONB и ищутся оператором `@>`.
Поскольку индексов нет, то на каждый такой поиск идет просмотр всей таблицы с разбором JSON.

### Структура данных в БД
Покупатели, сделки, контакты и компании лежат массивами в одной JSONB-строке.  
Следовательно:
- нет внешнего ключа «сделка-покупатель»
- нельзя создать индекс на `login`/`name`
- любое изменение одного элемента — перезапись всего JSONB

### Чистка
Чистка выполняет делает 1 `DELETE`, затем читает читает всю таблицу, изменяет данные и на каждый элемент делает `commit`.

### Остальные баги
- Чистка запускается, даже если сбор прервался.
- `Lead` не разбирает полученные данные `_embedded`, поэтому контакты сделок пусты и очищаются.
- У новых `AbstractCustomer` `id=None` до `commit`, поэтому чистка удаляет всех только что созданных `AbstractCustomer`.
- После слияния сделка помечается как измененная и удаляется, а должна сохраняться.

### Оценка количества запросов
При 20 тыс. покупателей и 50 тыс. сделок это **200-300 тыс. запросов + минимум 70 тыс. коммитов**.


## Что изменено

### Схема БД (`models.py`, `schema.sql`)
- Созданы модели `Customer`, `Lead` с `id`, `crm_*_id`, `login` и  другими ключевыми полями.
Ответ CRM записывается в сыром виде в `jsonb_data`.
- Введено поле `last_seen_run_id`, которое указывает, встречалась ли запись в текущем прогоне.
- Созданы индексы по `login`, `name`, `customer_id`, `last_seen_run_id`.
- Старая схема удалена.

### Запись в БД (`repository.py`)
- Запись в БД осуществляется пакетами по 1000 штук.
- Методы `upsert_customers(rows, run_id)` / `upsert_leads(rows, run_id)` - записывают в БД пакет:  
1 `INSERT ... ON CONFLICT ... DO UPDATE` на весь пакет.
- Методы `load_customers_data()` / `load_leads_data()` - загружают данные в словари:  
по 1 `SELECT` на пользователей и сделки.
- Метод `merge_customers(first_id, second_id)` - переносит сделки, объединяет
  `jsonb_data.contacts/companies` и `send_methods`, удаляет `second`.

### Чистка (`repository.py`)
- Метод `cleanup(run_id, contact_ids, company_ids)`:  
4 запроса: 2 `DELETE` на сделки и покупателей и 2 `UPDATE customer` с `jsonb_set` 
  (вычищает вложенные контакты/компании не из прогона и элементы с «удалить» в имени).

### Клиент CRM (`amocrm.py`)
- Метод `BaseEntity.from_api()` - разбирает один объект ответа, приводит `custom_fields_values` из списка API к словарю по имени поля, отсутствующие поля
  заполняются `None`.
- Метод `BaseEntity.to_json()` - создает JSON для `jsonb_data`.
- Метод `Lead.__init__` разбирает `_embedded` контакты/компании.

### Точка входа `collect_leads_customers(is_full=True)` (`main.py`)
- Методы `iter_customer_batches()` / `iter_lead_batches()` - читают из CRM паектами по 1000.
- Методы `sync_customers()` / `sync_leads()` - фильтры, поиск покупателя, слияние при расхождении, пакетное обновление,
  1 `commit` на пакет.
- Методы `collect_leads_customers()` - генерирует `id` прогона, два цикла по пакетам, сбор `id` за прогон, флаг `completed`
- Только при `completed and is_full` запускается чистка и `commit`. При исключении чистка не запускается.

### Остальное
- `config.py` - конфигурация БД и создание приложения Flask.
- `schema.sql` - SQL для создания таблиц.
- `requirements.txt` - добавлен `psycopg`.

### Оценка количества запросов
Теперь запись идет пакетами по 1000, поэтому на 70 тыс. сущностей это **140-150 запросов + 70-80 коммитов**.

## Что оставлено
- `jsonb_data` с ответом CRM. Поля, которые не переводятся в колонки, не теряются. Поиск и связи идут по колонкам.
- Контакты и компании внутри `jsonb_data` покупателя. Они ищутся при чистке, которая делает это одним запросом. Отдельные таблицы дали бы больше кода и внешних ключей.
- Пагинация и повтор запросов в `amocrm_get`.
